# Contributing to expo-ble-kit

Thanks for helping. The project is pre-alpha and follows a written plan: [docs/ARCHITECTURE_AND_PLAN.md](docs/ARCHITECTURE_AND_PLAN.md). Read §0, §3 (decisions) and Appendix B (engineering rules) before your first change.

- Work is organized as tasks in §7 (`P<phase>-<nn>`). Pick a task whose dependencies are done, or open an issue first for anything not in the plan.
- `[GATE]` items are decisions for the maintainer. Don't decide them in a PR; raise them in an issue.
- Facts marked `⚠️ VERIFY` must be confirmed against official Apple, Android or Expo documentation before you rely on them. Link the source in your PR and update the plan.
- If your code has to diverge from the plan, update the plan in the same PR.

## Setup

You need Node (version in `.nvmrc`), Xcode 26 or newer (Xcode 27 for iOS 27), the Android SDK with JDK 17, and [uv](https://docs.astral.sh/uv/) for the test peripherals. SwiftLint and ktlint are optional locally (`brew install swiftlint ktlint`); CI runs them.

Yarn is pinned in the repository (`.yarnrc.yml` and `.yarn/releases`). The repository root (the library) and `example/` are separate Yarn projects.

```bash
yarn install
yarn prepare                 # builds src/ -> build/ and plugin/src -> plugin/build
cd example && yarn install
cd example && npx expo prebuild --clean   # generates example/ios and example/android (gitignored)
cd example && npx expo run:ios            # or run:android
```

The example app's native folders are generated by the config plugin in `plugin/`. Never edit `example/ios` or `example/android` by hand.

Native code is split into a BLE **core** (`ios/Core`, `android/.../core`) and a thin Expo **binding** (`ios/Binding`, `android/.../binding`). The core never imports Expo or React (plan §4.1): on iOS it also builds as a standalone Swift package (`ios/Package.swift`), and on Android a unit test fails on such imports. Core code talks to CoreBluetooth and `android.bluetooth` only through the abstractions in `CBAbstractions.swift` and `BtAbstractions.kt`, so its tests run against fakes without a device.

Bluetooth doesn't work in the iOS Simulator. iOS Bluetooth behavior can only be tested on a real iPhone.

## Checks and tests

| What | Command |
|---|---|
| Lint, format, types | `yarn lint`, `yarn format:check`, `yarn typecheck` |
| Native lint | `yarn lint:native` |
| L1: TypeScript unit tests (Jest) | `CI=1 yarn test` |
| L2: native unit tests (iOS core) | `swift test --package-path ios` |
| L2: native unit tests (Android core) | `cd example/android && ./gradlew :expo-ble-kit:testDebugUnitTest` (after `npx expo prebuild`) |
| Test peripheral (Bumble) | `cd test-peripherals/bumble && uv run pytest` |
| L3: Android emulator + virtual radio | `e2e/android-netsim/run.sh` with an emulator running (see `test-peripherals/README.md`) |
| L4: real phones and boards | before releases, see plan §8 |

`test-peripherals/profile.json` defines the test GATT profile for every test peripheral. Change the profile first, then the implementations.

## Pull requests

- Keep each PR to one task or fix.
- Follow the checklist in the PR template (the plan's Definition of Done): tests, types, docs, the example app still builds on both platforms, and a changeset.
- A changed public API also updates plan §5 and `src/types.ts` in the same PR.
- Never weaken a rule, timeout or test to make CI pass. Open an issue instead.

### Changesets

Run `yarn changeset` for any change users will notice, choose the bump type, and write the changelog entry. Before 1.0 each phase ships as a minor version on the `next` dist-tag.

## Reporting bugs

Use the bug report form. Debug logs (`BleManager.setLogLevel('debug')`) and `BleManager.getDiagnostics()` output make most problems much faster to fix. Report security problems privately, as described in [SECURITY.md](SECURITY.md).
