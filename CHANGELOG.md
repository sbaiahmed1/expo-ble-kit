# expo-ble-kit

## 2.0.0

The first stable release, on npm's `latest` tag: the central role on iOS, Android and the web, the peripheral role, background work on both platforms, L2CAP channels, the system device pickers, a react-native-ble-plx compatibility layer and an agent skill. What has run on which hardware, and what hasn't yet: `docs/compatibility.md`.

### Minor Changes

- ce3da10: iOS 18+: `BleManager.ios.showAccessoryPicker(items, { timeoutMs })` shows AccessorySetupKit's picker with the nearby accessories that match `items` (an advertised service or company id, optionally a name substring, masked manufacturer or service data, and immediate range). The person's pick authorizes that accessory for the app without the Bluetooth permission prompt; the call resolves its `Peripheral`, or null when nothing was picked. The config plugin's new `ios.accessorySetupKit` option writes the Info.plist declarations (never an empty list: iOS stops the app on one), and the call rejects with `MISCONFIGURED` when an item uses an identifier they don't list or a list is malformed (iOS would stop the app). Declaring AccessorySetupKit changes how Bluetooth works for the whole app, measured on iOS 27.0.1: no prompt, scans see only picked accessories, and the adapter reads `poweredOff` until the first pick. In such an app the library uses the central manager without the prompt, and `getPermissionsAsync()` reports scanning and connecting as granted. See the new guide, `docs/guides/accessory-setup.md`. The testing fake picks the first advertising virtual peripheral that matches (`injectError` op `showAccessoryPicker`).
- 32d6296: The package ships an agent skill, `skills/expo-ble-kit/SKILL.md`, with recipes for a heart rate monitor, streaming and firmware-style transfers, and background work and reconnection. In an Expo app, `npx @expo/agent-cli skills:sync` links it where coding agents (Claude Code, Codex and others) find it.
- ee49bca: Bonding: `peripheral.android.createBond(options)` bonds with a connected Android device (queued with the GATT operations; Android's pairing dialog asks the user, and the library never confirms a pairing itself), and `peripheral.android.bondState` reads `'none'`, `'bonding'` or `'bonded'`. A refused or failed pairing rejects with `BOND_FAILED`. On iOS, which pairs by itself when an attribute needs encryption, `bondState` is `'none'` and `createBond` rejects with `NOT_SUPPORTED`. The testing fake bonds connected virtual peripherals (`injectError` op `createBond`).
- 691ada7: Android companion devices: `BleManager.android.associateCompanionDevice(filter)` shows Android's companion device picker and resolves the picked device's `Peripheral` (or null), without the Bluetooth scan permission. Background tasks can now receive `devicePresence` on Android 12+: Android starts the app when an associated device comes into range or leaves it. Turn it on with the config plugin's `android.companionDevice` option (bare apps: see the bare-setup guide). `BleManager.android.isLocationServicesEnabled()` tells whether Location Services are on, which scans on Android 11 and older and the companion picker need.
- ce80d36: iOS background: with the config plugin's new `ios.backgroundModes: ['central']`, iOS keeps the app's connections, scans and notifications going in the background, and `connect({ keepAliveInBackground: true })` works on iOS (it needs that mode). With `ios.restoreIdentifier` as well, CoreBluetooth state restoration is on: when iOS stops the app, it keeps its connections and relaunches it in the background for their events, and the library hands them back at launch (connected ones `connected` with their notifications still on, pending ones `connecting`). `registerBackgroundTask` now works on iOS with the `restored`, `notification` and `connectionStateChange` events, delivered to an `expo-task-manager` task in order (measured on iOS 27: after a system termination the relaunched app's task received every notification). `getDiagnostics().ios.restoration.journal` records what happened around background relaunches, kept across launches.

  The peripheral role survives too: with `ios.backgroundModes` including `'peripheral'`, iOS keeps the GATT server's services and the advertisement while the app isn't running, relaunches the app for a central's requests, and an `openGattServer` with the same services at the next start takes the restored server over (requests that arrived in between wait for it).

- 942d04e: L2CAP channels: `peripheral.openL2CAPChannel(psm, options)` opens a connection-oriented channel to a connected peripheral, and `BleManager.publishL2CAPChannel({ secure })` publishes a server that centrals open channels to. An `L2CAPChannel` is a byte stream: `write()` resolves once the system took the bytes, reading starts with the first data listener (flow control holds the peer back until then), and the close listener says why it closed. Android needs version 10. `expo-ble-kit/testing` gains L2CAP on virtual peripherals (`publishL2CAPChannel`) and a virtual central side (`FakeBle.openL2CAPChannel`).
- c85723d: `expo-ble-kit/compat/plx`: react-native-ble-plx 3.5.1's API (`BleManager`, `Device`, `Service`, `Characteristic`, `Descriptor`, `BleError` with its numeric codes and messages, base64 values, transaction ids) over expo-ble-kit, so an app moves by changing its imports. The differences are listed in the new migration guide, `docs/guides/migration-from-plx.md`.
- c5e1cab: Android: `peripheral.android.requestConnectionPriority('balanced' | 'high' | 'lowPower')` asks for a connection interval, and `peripheral.android.setPreferredPhy(tx, rx, codedOption)` asks for the 1M, 2M or coded PHY and resolves the PHYs the link uses. Both are queued with the GATT operations; on iOS, which chooses by itself, they reject with `NOT_SUPPORTED`. When Android doesn't report a PHY update (it may not when nothing changes), the library reads the PHYs instead of waiting for the timeout.
- 6021655: The web: in Chrome and Edge, the central role works over Web Bluetooth. A scan opens the browser's device chooser (it needs a tap just before), and the picked device is its one result; connecting, discovery, reads, writes, `writeStream`, descriptors and notifications then work as on phones, one operation at a time. `ScanOptions.web.optionalServices` names the other services the page will use, since the browser only allows those named in the scan. What browsers can't do (MTU, RSSI, reconnection policies, the GATT server, advertising, L2CAP, background tasks) rejects with `NOT_SUPPORTED`; without Web Bluetooth the state is `unsupported`.

## 0.1.1

### Patch Changes

- iOS: `pod install` failed with 0.1.0 ("undefined method '=~' for an instance of Hash"): the podspec read `repository` from `package.json` as a string, and it is an object. It now takes the object's URL.

## 0.1.0

### Minor Changes

- c9324ab: First preview of expo-ble-kit, Bluetooth Low Energy for Expo and React Native. The central role: permissions and adapter state without surprise prompts, scanning with filters (several scans share the radio), connections with timeouts and `AbortSignal` cancellation, service discovery, reads and writes (long ones too), descriptors, notifications and indications, MTU and RSSI, typed errors (`BleError` with a `code`), UUID helpers and constants, the React hooks `useBleState`, `useBlePermissions`, `useScan`, `usePeripheral` and `useCharacteristicValue`, a config plugin for the permissions, and `expo-ble-kit/testing`, a fake Bluetooth stack for Jest. The other entries of this release add to it.
- 0048cd0: Advertising: `BleManager.startAdvertising(data, options)` advertises the phone as a peripheral on iOS and Android, one advertisement at a time, and resolves with an `Advertisement` to `stop()`. iOS advertises the local name and service UUIDs; Android also advertises manufacturer data, service data and the TX power level, with `android` options for the interval, transmit power, extended advertising and a timeout, but only the phone's own Bluetooth name. What a platform can't advertise is reported as a `NOT_SUPPORTED` warning. New config plugin options: `android.advertise` declares `BLUETOOTH_ADVERTISE`, and `ios.backgroundModes: ['peripheral']` adds the `bluetooth-peripheral` background mode. The testing entry gains `FakeBle.advertisement`.
- aa57edf: Android: `BleManager.registerBackgroundTask(taskName, { events: ['scanResults'], scan })` runs a background scan that delivers matching advertisements to an `expo-task-manager` task, waking the app even after Android stopped it; `unregisterBackgroundTask` stops it. On Android 10–11 it needs background location: the config plugin declares it with `android: { backgroundLocation: true }`. New types `BackgroundTaskOptions` and `BleBackgroundEvent`. On iOS, `registerBackgroundTask` rejects with `NOT_SUPPORTED` for now.
- 362f428: Service changes: when a connected peripheral's services change (iOS, and Android 12+), the library discovers them again, keeps the subscriptions that are still possible, and calls `peripheral.addServicesChangedListener` listeners. `peripheral.android.refreshGattCache()` clears Android's GATT cache and discovers again (hidden API, resolves `false` where unavailable). The Android connect option `android.resetAfterTimeouts` sets how many operations in a row may time out before the connection is reset (default 2, `false` to never reset), and a reset now reconnects when a `reconnect` policy is set.
- ac2d24c: Peripheral role: `BleManager.openGattServer(services)` publishes a local GATT server on iOS and Android. Static values are answered natively; `onReadRequest` and `onWriteRequest` handlers answer the rest within 25 s (else an ATT error and a warning). Long reads are served from one handler result per read sequence, long writes arrive as one value, thrown `BleError`s become ATT errors, and `addSubscriptionListener` reports CCCD subscriptions. The testing entry gains `connectCentral()`, a virtual central for testing server handlers. Advertising comes next.
- e2b635d: Android: `connect({ keepAliveInBackground: true })` keeps the app running in the background while the connection is open, with a foreground service of type `connectedDevice` that stops when the connection ends (reconnecting keeps it). Enable it with the config plugin option `android: { foregroundService: true }`; set its notification with `BleManager.android.setForegroundServiceNotification()`. A start Android refuses (the app was in the background) sends a `FOREGROUND_SERVICE_FAILED` warning. `getDiagnostics().android.foregroundService` tells whether it runs. On iOS the option still rejects with `NOT_SUPPORTED`.
- 9991e6d: Logging: `BleManager.setLogLevel(level)` and `BleManager.setLogHandler(handler)`. At `debug`, every GATT operation logs its id, kind, status and duration; `info` adds connection states and scans, `verbose` notifications. Logs go to Logcat (tag `BleKit`) and the iOS unified log (subsystem `expo.blekit`), and to the handler while one is set. A failed fire-and-forget `subscription.remove()` is logged as a warning.
- 09bdf35: `Peripheral.subscribeBatched(service, characteristic, onBatch, { intervalMs, maxItems })` collects notifications natively and delivers them at most once per `intervalMs`, each value with the time it arrived, so fast sensors don't flood the JS thread. When more than `maxItems` (default 4096) arrive in one interval, the oldest are dropped and counted in `dropped`, with a new `BUFFER_OVERFLOW` warning.
- f53b599: Reconnection policies: `connect({ reconnect: { maxAttempts, initialDelayMs, maxDelayMs, backoff } })` brings a lost connection back by itself, through the new `reconnecting` state, and restores subscriptions before `connected` (`restoreSubscriptionsOnReconnect`). On iOS 17 and later, `ios.enableAutoReconnect` lets the system reconnect first.
- 72e278b: GATT server notifications: `GattServer.notify(characteristic, value, { centrals })` sends a notification, or an indication to centrals that asked for one, to the subscribed centrals. It is flow-controlled on both platforms (Android waits for `onNotificationSent` per central and retries a busy stack, iOS waits for `peripheralManagerIsReady`), so awaiting each call paces a stream to the link. Values longer than a target's MTU − 3 reject with `INVALID_ATTRIBUTE_LENGTH`, a value waits at most 10 s, and centrals that disconnect drop out. The testing entry's `VirtualCentral` gains `notifications`.
- 99e825c: `Peripheral.writeStream(service, characteristic, data, options)` sends a payload of any length in chunks of one packet, natively and with flow control: `onProgress` reports about every 1 %, an `AbortSignal` stops it within the chunk in flight, `withResponse: true` acknowledges each chunk, and `chunkSize` makes chunks smaller. Operations issued during a stream wait until it ends.
- 271b3b3: Writes without response are flow-controlled: they resolve once the phone's Bluetooth stack took the packet and wait while it is full, so bursts are neither dropped nor failed. On Android a congested link no longer fails a write with `CONGESTED`, and a packet the stack refused while congested is sent again; on iOS a write that timed out while waiting is no longer sent later.

### Patch Changes

- b71e798: `getDiagnostics().sessions[].subscriptions` now counts each connection's active subscriptions; it was always 0.
- 9e82df4: Android: fixed a crash (`ConcurrentModificationException` in the scan controller) when many scan results arrived during a `reportIntervalMs` window. Scan results now reach the library's Bluetooth thread like every other callback.
